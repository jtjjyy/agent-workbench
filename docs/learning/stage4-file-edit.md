# 第四阶段：文件执行器学习记录

## 接口边界

`createFileEditTool(workspace, onEdit)` 注册 Pi 工具 `replace_text`。工具参数严格限定为 `path`、`oldText`、`newText` 三个普通字符串字段：路径只能是工作区内已有白名单 UTF-8 普通文件的相对路径；`oldText` 非空且必须在完整正文中唯一出现；`newText` 可以为空，但前后不能无变化。

主 Agent 通过 `onEdit(proposal, apply, signal)` 管理审批和日志。提案为 `FileEditProposal`，包含完整的 `beforeText`、`afterText` 以及原始字节 SHA-256。提案中的 UTF-8 BOM 会保留为开头的 `\uFEFF`，因此 `Buffer.from(beforeText, 'utf8')` 和 `Buffer.from(afterText, 'utf8')` 可直接对应原始字节哈希，且 BOM 计入 32 KiB 和 12000 UTF-16 单元上限。工具结果只返回状态、相对路径和哈希，不返回完整正文或处理器原始摘要。

`onEdit` 抛出的错误不在工具内部转换；它会继续向主运行时传播，由主运行时按日志失败或 `unknown` 规则中止任务。`apply(signal)` 一次性消费，重复调用不会重放写入。

## 复用的安全策略

`readonly-tools.ts` 现在导出公共的工作区上下文、路径检查、父链与文件身份比较、有界 UTF-8 读取和解码接口。文件执行器复用敏感目录、文件白名单、相对路径、工作区根指纹、真实路径和符号链接拒绝规则，并额外要求目标文件 `nlink === 1`。准备和审批后执行都重新核对根、父目录链、文件身份、元数据与完整字节哈希。

## 写入策略和实际边界

批准后使用同一文件描述符以 `O_RDWR` 打开，语义相当于 `r+`：不创建、不预先截断。先复查原始字节，再以单次有界写入覆盖正文；缩短文件时，复查已经写入且将被保留的目标字节后才调用 `truncate`。随后同步并通过同一描述符重新读取、复查目标路径身份和目标 SHA-256。

写入调用发生异常、短写、截尾、同步或复读无法确认时，结果为 `unknown`，不补写、不重试、不自动回滚。写入前取消返回 `cancelled`；正文已经写完后即使收到取消，只要同步和复读确认目标字节，返回 `applied`，并明确这不代表回滚。该检查仍不能提供跨进程 compare-and-swap，也不是操作系统沙箱；检查和写入之间仍存在同权限进程竞态，断电和文件系统异常可能留下未知结果。
